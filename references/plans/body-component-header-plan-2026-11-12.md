# 正文组件与公共页眉解耦实施计划书

版本 **v1.2** · 修订日期 **2026-11-20** · 当前阶段 **知识库正文资产改造**

## 1. 目标与实施原则

知识库直接保存已拆去页标题、Logo 和公共装饰的可编辑正文组件。生成时按内容选择纯正文组件，技能再与兼容的公共页眉组合。组件的正文文件和独立绑定需要可直接检查。

开发、试点和优化均在独立分支与工作目录完成，达到本计划的稳定条件后再合并 main。当前交付限于计划和分支准备；本文件中所有新接口、文件名和阶段产物均为拟议设计，不能视为已有功能。

核心原则：

- 保持材料事实完整、原生对象可编辑、组件图形关系正确。
- 技能管理页标题、Logo、公共装饰、画布和安全区；知识库管理正文图形及其字段、几何和能力记录。
- 普通正文按结构匹配；专用语义、真实项数、图表数据和正文容量约束继续有效。
- 将已验收的纯正文资产及其绑定作为配套技能的默认组件来源。来源整页作为溯源和旧版本兼容记录。
- 封面、目录、章节、封底继续走专用整页模板流程。
- 同一稿统一主题和默认页眉；确需使用兼容变体时记录原因，避免逐页随机更换。

## 4. 技术方案

### 4.1 公共框架登记

拟在技能中建立版本化框架登记，复用现有品牌资产与布局基础，避免维护两套互相矛盾的默认值。拟议字段：`frame_id`、`frame_version`、`theme`、`style_family`、`canvas`、`title_variants`、`logo_asset`、`logo_box`、`body_safe_regions`、`reserved_regions`、`font_profile`、`source_reference`。

第一批建立简约和科技两个框架族。标题宽窄与 Logo 位置作为受约束变体，不机械生成所有排列组合。选择优先级：用户明确指定且兼容的变体 → 整稿默认变体 → 同族已验证替代变体；没有兼容项时返回具体原因。

标题容量按实际字体、字号、行数、文本宽度和安全区计算，再通过目标应用渲染确认。不得新设一个全局“最多 11 字”替代所有原限制。短、边界、长标题及中英数字混排分别验收；过长时优先使用已验证加宽或双行变体，仍不适配则报告。双行变体在验证前不开放；不得自动删字或无限缩小字体。

### 4.2 正文组件拆分

逐页辨认：公共标题、Logo、公共装饰、正文对象、内部标题和无法独立拆分对象。对象定位必须包含源文件/页面、对象 ID 与组路径；母版及版式对象单独登记，避免重名或组内 ID 误删。

拟以增量 `body_component_contract` 登记每个主题实际使用的来源路径、页号和哈希，以及保留／移除对象、正文边界、兼容框架、背景或母版依赖、验证状态和证据。已登记 `ready_source_by_theme` 时，以该修整单页为实际定位依据，原稿定位留作追溯。对象位置和依赖须用实际选中的文件核对。首批固定正文坐标与比例，图表、工作簿、图片、SVG 回退和关系随原生页保留。

后续如增加平移或等比例缩放，须按组件登记许可并重新检查字号、线宽、图标、连接线与可编辑性。背景图已烘焙标题或 Logo、顶部与正文难以拆分的页面登记为整页例外。

沿用源组件 ID。只有已核验的公共页标题绑定由技能接管。正文内部标题、中心论点、分组和条目标题、图表标题与图例按实际语义保留。P244 的 `center.subtitle` 仍走现有可选字段规则。对象归属根据语义、组路径、位置和正文边界综合判断，科技风中位于正文区域的 `heading` 单独登记。

### 4.3 选版、填充与组装

新路径：锁定主题与字体 → 读取独立页标题 → 按正文关系、项数和字段选组件 → 校验正文容量 → 选兼容框架 → 填充正文 → 添加公共框架 → 组装 → 审计与视觉验收。

复用当前适配和容量检查，在选版、预检和填充三个环节统一应用同一份已确认的替换契约。新路径按公共框架容量检查页标题，正文继续检查自身必填字段、容量、项数和数据契约。旧整页路径按原模板绑定执行。已有请求中的标题字段通过明确映射兼容，若同时提供新旧字段且内容冲突，报告具体冲突。

维护端在知识库构建时按已核对的来源哈希、对象定位、主题、画布和净空，提前拆出可编辑的 `body-*.pptx` 和独立正文绑定，再一并登记到清单。技能直接读取纯正文文件，核对资产和绑定哈希后添加页眉。未登记或尚未验证的资产保留原路径。覆盖统计以实际出版的纯正文资产及其主题数为准。

每页记录纯正文来源提交、路径、哈希和框架版本。维护契约中另记原稿与离线删除的对象。来源审计核对实际读到的纯正文文件及页来源戳，结构页继续按原目录审计。

### 4.4 新旧兼容与离线

知识库先增量提供契约与必要资产，现有整页资产继续支持旧技能。新技能读取旧知识库时走旧路径，并记录无对应契约。契约版本不支持时拒绝该组件的替换路径，并在原条件适用时尝试整页路径。

开发期用显式开关和试点组件清单启用替换。验收后按组件和主题开放默认使用。单次任务固定知识库提交。离线完整缓存按所含契约和资产决定可用组件，最小包按实际可用范围报告。

发布阶段统一生成技能与知识库清单，验证 Git 归档、LF/CRLF 检出、完整缓存与最小包。运行期不重写哈希绕过校验。

## 5. 维护兼容性、分支与合并

### 5.1 维护工具兼容验证

用维护仓库 `7cf3553` 对正式技能 v1.0.34 执行 `maintain.py --skill-root <技能副本> --list`，首项失败为 `SKILL_RUNTIME_INCOMPATIBLE: scripts/assemble_native.py`。按维护器现有源码规范比较，61 个登记文件中有 18 个哈希与正式版不同。这个结果定位到兼容登记与正式源码不匹配，具体工具行为须通过复验确认。

1. 在隔离目录固定维护仓库、技能正式版和知识库提交，保留原记录。检查 18 个差异文件与工具依赖，尤其是填充、选版、原生组装和审计。
2. 在维护分支建立正式版候选兼容配置，按现有源码规范计算候选哈希。以候选配置通过 `maintain.py --list`，并针对改动依赖实际跑工具和运行回归。
3. 对知识库副本检查清单，验证更改后的清单重建、固定提交打包、安装包校验与隔离安装。记录真实工具结果、使用的三仓提交和样本。复验通过后，才将该配对写成已验证兼容。
4. 试点分支若改变维护工具依赖的运行模块，用同样流程复验候选配对。保留启动器兼容检查，分发文件仍按原始字节校验。

### 5.2 独立分支与合并顺序

本次 v1.1 文档在现有 `feature/body-header-variants` 分支管理。该分支从旧版技能创建，保留既有计划历史。实施启动时，从三仓各自最新并经核验的 `main` 建独立实施分支和工作目录，带入计划文档，记录选定的三仓配对提交。可沿用知识库原分支的用途命名。如果旧分支或工作目录仍存在，先确认其差异再决定复用。

开发、试点和清单构建显式指定隔离目录与固定提交，输出、缓存和测试安装与正式环境分开。各阶段独立提交，记录每次跨仓验证所用的提交对照。当前跨平台组装已进入 v1.0.34，S0 以现有后端实测基线为准，无需等待旧跨系统分支合并。

先在三个开发分支完成兼容验证与蓝红试点，再按第 7 节条件决定发布范围。合并顺序为维护端兼容与工具、知识库向后兼容增量、技能对新旧契约的支持，最终开放已签收组件的默认路径。每次合并前同步最新 `main` 并对齐受影响的配对，合并后核对实际提交、清单和发布包。

## 7. 验收与稳定定义

### 7.1 蓝红试点验收

| 验收项 | 通过条件 | 证据 |
| --- | --- | --- |
| P112 长标题解耦 | 蓝红两版各用同一组四项正文复现旧路径 11 字通过、12 字被页标题拒绝。新路径 11 字与同一 12 字标题均实际填充，PowerPoint 显示完整，四组标题和说明仍对应、可编辑。另测 14 字、中英数字混排及超过框架实测容量的样本，记录适配或拒绝原因。 | 蓝红的旧/新预检、原生单页和 PowerPoint 导出图。 |

验收将生成候选、PowerPoint 打开导出、逐页视觉复核分别登记。通过以与最终文件哈希对应的导出图及实际复核为依据。后续开放图表、表格或科技风复杂组件时，追加相应原生编辑、图表工作簿、背景和母版依赖验证。

### 7.2 回归矩阵

| 维度 | 必测内容 | 证据 |
| --- | --- | --- |
| 主题 | 蓝、红、科技 | 各框架及 Logo 变体对照图 |
| 文本 | 短标题、边界标题、长标题、中英数字、换行；正文短/长 | 输入、实际字号/行数、渲染结果 |
| 对象 | 普通形状、组合、母版依赖、图表、表格、SVG | 原生编辑抽查及包审计 |
| 版本 | 新技能×新库、新技能×旧库、旧技能×兼容新库 | 配对提交与执行报告 |
| 网络 | 在线固定提交、已验证完整缓存、仅最小包、哈希损坏 | 来源标记和准确失败原因 |
| 系统 | Windows PowerPoint 正式路径，macOS/Linux 默认原生组装路径 | 记录生成、静态检查、实际渲染和视觉结果各自的验证状态 |
| 材料 | 沈阳文档蓝色整稿与红色相关页；扩展后按影响范围回归原有材料及主题 | 同事实与逐页请求基线下的新旧产物和指标 |

本机不能替代 Mac 实机视觉验收；实施时复用跨系统任务的环境与测试入口。Mac 未完成的结果明确标记待验收，不扩大跨平台支持声明。任何已正式支持平台被此改动影响，都需补齐该平台验收后方可正式启用。

### 7.3 指标口径

分别记录已迁移组件数、真实复用页数、仅因旧页标题被拒的候选次数与影响页数、回退原因及最终视觉通过页数。仅当同一次候选检查的其他约束均通过时，才将拒绝归因于页标题。实际复用率以最终成稿中成功填充知识库正文组件的页数除以正文总页数。蓝红变体按结构统计时只计一次，候选召回和实际填充分别记录。

材料覆盖同时核对整稿事实覆盖及知识库正文承载的事实覆盖。分母为基线固定的源事实单元，分子为对应范围内正确承载的事实单元。页面改为技能排版时，仍计入整稿事实覆盖；知识库正文承载口径仅统计实际复用页。复用率提升幅度以 S0 的真实材料基线为准。

### 7.4 合并 main 的必要条件

1. 合并范围内 S0 至 S4 的阶段记录齐全，维护端已验证当前三仓配对。未进入本次范围的组件记录为例外或待评估。
2. 已开放新路径没有事实丢失、文件损坏、原生对象破坏、品牌错误、可见碰撞等阻断问题；所有例外明确关闭新路径或修复。
3. 最终配对候选完成与本次开放范围对应的回归矩阵。缺陷修复后重测受影响项，并使用干净目录重复关键端到端流程，结果一致。
4. 保留原正文长文案与结构语义验收；字体、几何、容量或换行受影响的组件补测，不直接继承为已通过。
5. 同步最新 main 后，针对冲突和依赖变化复验；清单、归档与安装路径通过，回退验证完成。
6. 具有实际渲染和逐页视觉复核记录；`ready`、程序退出成功或 ZIP 可解压都不替代交付验收。

## 8. 工作量与风险安排

首批蓝红试点估算 **4–7 人日**，包括维护兼容基线、两种组件、真实材料和 PowerPoint 验收。若继续覆盖完整范围，累计暂估 **12–22 人日**。科技风的背景、母版和内部标题需要逐页处理时，以 S3 首批实测重新估算。实机反馈等待时间另计。

主要成本在对象识别、背景/母版依赖、逐页视觉验收和兼容发布，公共页眉绘制本身只占部分工作。Token 随例外数量、日志长度和修复轮次变化，本计划不将固定 token 数作为完成或合并门槛；执行时按阶段记录实际使用量（平台可提供时）。

| 风险 | 处理方式 |
| --- | --- |
| 误删内部标题 | 语义与对象定位双重核对；两个科技 heading 作为固定负例 |
| 宽标题侵入 Logo 区 | 使用实测净空选择变体；宽度不同不等于可以无条件加宽 |
| 背景烘焙标题或 Logo | 登记整页例外，另做可编辑重构评估 |
| 新框架压缩正文 | 安全区兼容筛选；允许变换须重新渲染，不统一缩小全部正文 |
| 维护工具配对滞后 | 用最新正式技能复验维护工具与回归入口，兼容记录随已验证的三仓提交更新 |
| 清单或版本错配 | 配对版本、兼容声明、发布期清单生成、运行期严格校验 |

## 9. 回退与最终交付

实验期关闭新路径即可回到旧整页流程。正式发布保留上一配对版本、旧整页资产和必要缓存；出现问题时先停用受影响组件的新能力，必要时回退技能和知识库配对版本。禁止以删除共享缓存、强制改写 main 历史作为常规回退。

最终交付包括本计划、版本化框架与组件契约、独立正文资产与绑定、迁移台账、可编辑对照稿、真实材料验证、三仓兼容及测试记录、发布和回退说明。
